# GitHub Release 安装脚本实践

本文总结 `install_fd.sh` 与 `install_ripgrep.sh` 采用的通用原则，适用于为 Linux 命令行工具编写“最新版优先、低依赖、兼容国内网络”的安装器。

## 目标与边界

安装器首先要明确默认策略。对于单文件 Rust/Go CLI，官方预编译 Release 往往比发行版仓库更新，也比源码编译依赖更少，因此适合作为默认路径。发行版包管理器可以作为明确需要的后备选项；Cargo、npm、pip 等外部生态安装器或源码编译只有在需求明确时才实现，避免无谓扩大依赖、网络源和维护边界。

建议按以下顺序设计：

1. 默认安装官方最新预编译二进制。
2. 允许固定版本，便于复现；若低于已安装版本则拒绝。
3. 显式提供发行版包模式，适合偏好系统统一维护的机器。

脚本不应擅自启用 EPEL、Copr、PPA 等第三方系统仓库，也不应静默安装完整编译工具链。这些行为会改变系统的长期信任和维护边界。

## 平台与资产选择

不要仅将 `uname -m` 拼进文件名。Release 项目通常使用 Rust target triple，需要同时考虑：

- CPU：x86_64、aarch64、armv7、i686、s390x 等。
- libc：glibc/gnu 与 musl。
- ARM ABI：soft-float、hard-float。
- 项目自己的文件命名和版本标签是否带 `v`。

映射必须以项目当前 Release 资产为依据，并在未知架构上明确失败。不能猜测一个文件名然后安装下载到的 HTML 错误页。

对真正静态链接的 musl 二进制，可以在 glibc 发行版上优先使用，从而降低旧系统的动态库要求；但要以项目官方构建说明为准。

## 最新版本解析

优先利用 GitHub 的稳定重定向：

```text
https://github.com/OWNER/REPO/releases/latest
```

从最终或中间 `Location` 中提取 tag，可以避免依赖 GitHub API、`jq` 和 API 限流额度。实现时仍需：

- 设置连接超时和总超时。
- 限制重试次数。
- 验证解析结果符合预期版本格式。
- 允许用户直接指定版本，在 latest 路径不可用时继续工作。

### API 与文件镜像必须分流

`https://api.github.com/` 应当直连，或通过 curl 的 HTTP/HTTPS/SOCKS 代理访问。不要构造成下面这种地址：

```text
https://gh-proxy.com/https://api.github.com/repos/OWNER/REPO/releases/latest
```

`gh-proxy.com` 等服务主要面向 `github.com` Release、archive、raw 文件和 Git 资源，对 REST API 的状态码、请求头、限流响应、分页和 JSON 内容没有稳定兼容承诺。即使某个节点暂时能返回 API 响应，也不应据此依赖。

如果安装器确实必须调用 GitHub API，应建立独立的 API 请求函数：

- URL 始终保持 `https://api.github.com/...` 原样。
- 允许 `--proxy` 或标准代理环境变量参与 curl 请求。
- 使用 API 要求的 `Accept`、版本和 User-Agent 请求头。
- 正确处理 `403`、限流、分页和超时。
- API 失败后可以退回用户指定版本或 `/releases/latest` 重定向，但不能退回文件镜像代理 API。

文件镜像 URL 构造函数也应主动拒绝 `api.github.com`，形成代码级防误用。当前 fd 和 ripgrep 脚本不调用 GitHub API，而是使用 `github.com/.../releases/latest` 重定向获取版本；`--mirror` 只作用于 Release 页面、归档和 checksum 文件。

## 国内网络与镜像

GitHub 加速服务常用以下 URL 形式：

```text
https://代理前缀/https://github.com/OWNER/REPO/releases/download/...
```

自动模式应复用仓库中的 [`net_is_cn.sh`](../shell_utils/net_is_cn.sh) 判断当前出口，并遵守这些约束：

- CN 出口优先少量已审核的文件镜像，最后用 GitHub 直连兜底；非 CN 或无法判断时优先直连。
- 一次安装只检测一次，`--verbose` 记录国家代码、区域分类和最终候选顺序。
- 地区检测失败或辅助脚本缺失不能阻断安装，应回退到直连优先。
- 显式选择 `--mirror` 时不做自动地区检测；显式 `--proxy` 时按代理的实际出口判断。
- 每个候选都有短连接超时，失败后继续下一项。
- 下载本身有合理的总超时与有限重试。
- 允许 `--mirror https://...` 使用用户审核过的节点或内网镜像。
- 允许 `--proxy` 使用本地 HTTP/HTTPS/SOCKS 代理。
- API 请求只允许直连或 `--proxy`，不能进入文件镜像候选列表。
- 日志显示正在使用哪个通道，但不能输出包含认证信息的代理 URL。
- 不远程获取一个不断变化的公益节点列表并全部自动信任。

[gh-proxy issue #116](https://github.com/hunshcn/gh-proxy/issues/116) 与 [GitHub 文件加速聚合页](https://yishijie.gitlab.io/ziyuan/) 可用于人工发现节点。聚合页声明节点来自网络收集，服务的可用性、运营者和内容安全都可能变化。节点列表适合“发现”，不适合直接成为安装器的信任根。

## 完整性与真实性

安全层次应区分清楚：

1. HTTPS 防止普通链路篡改，但第三方镜像是 TLS 连接的终点。
2. tar/gzip 格式检查只能发现损坏，不证明来源。
3. 执行 `tool --version` 可以防止错包，不能防止伪造程序。
4. 与归档一起经同一镜像下载的 `.sha256` 可发现传输损坏，但恶意镜像能够同时替换二者。
5. 用户从独立可信渠道提供的 SHA-256，或组织内部签名/证明，才能形成更强的信任锚。

如果上游发布独立的 checksum 文件，默认校验它；若未发布，则提供 `--sha256` 让用户固定可信摘要。不要编造校验值，也不要把“同源 checksum”描述成数字签名。

## 安全解压与安装

不要直接把整个未知归档解压到 `/usr/local`。推荐流程：

1. 使用 `mktemp -d` 创建独立临时目录。
2. 先列出归档成员，拒绝绝对路径和含 `..` 路径段的成员。
3. 只提取预期的唯一可执行文件。
4. 拒绝符号链接，要求目标为常规文件。
5. 运行临时二进制并核对精确版本。
6. 在最终目录创建同文件系统暂存文件。
7. 校验暂存文件后用 `mv` 原子替换。
8. 用 trap 在成功、失败和信号中断时清理临时文件。

若目标已存在但无法识别为预期工具，默认拒绝覆盖。只有用户显式传入 `--force` 后才替换。

## 已安装版本与更新策略

安装器必须先识别精确目标位置的现有程序并读取版本，再决定是否下载和覆盖：

| 本地与目标关系 | 默认行为 |
| --- | --- |
| 目标不存在 | 作为新安装继续，不询问升级确认 |
| 本地等于目标 | 跳过下载；显式 `--force` 可重装同版本 |
| 本地低于目标 | 视为升级，交互确认后继续 |
| 本地高于目标 | 视为降级，明确失败；不提供降级开关 |
| 现有文件无法识别 | 默认拒绝覆盖；`--force` 仅处理这种冲突 |

除非需求明确要求回滚，安装器不应实现降级功能。`--force` 与 `--yes` 都不能隐含允许降级，这可以避免把版本参数拼错后覆盖较新的程序。

交互与自动化规则：

- 交互终端在升级前显示当前版本和目标版本，默认回答为 No。
- 非交互环境遇到版本变化时明确失败，提示使用 `--yes`，不能等待 stdin 或静默升级。
- `--yes` 只跳过升级确认，不改变版本方向策略。
- dry-run 不等待输入，只报告正式执行时将请求何种确认。
- 用户拒绝更新时返回成功且不修改现有程序，临时文件仍应清理。

版本比较应按数值段而不是字符串排序，否则会错误判断 `1.10.0` 与 `1.9.0`。若接受预发布版本，还应遵循 SemVer：同一核心版本的预发布版本低于稳定版本，并逐段比较预发布标识。

默认 binary 模式可以从 Release 明确得到目标版本，因此能够完整执行上述策略。系统包模式不指定包版本，应交由包管理器求解升级并阻止降级；默认保留包管理器自己的确认提示，只有 `--yes` 才传递其非交互确认参数。未被明确要求的 Cargo 等外部安装路径不应仅因上游文档列出而加入脚本。

## 权限与安装位置

合理的默认值是：

| 身份 | 默认目录 |
| --- | --- |
| 普通用户 | `~/.local/bin` |
| root | `/usr/local/bin` |

普通用户安装不应自动提升为 root。系统级安装由用户显式执行 `sudo ./script`。自定义安装目录必须是绝对路径，脚本完成后应检查目录是否位于 `PATH`。

卸载必须是精确、可预测的：只删除当前模式和当前安装目录对应的文件，不要在 PATH 或整个文件系统中搜索并删除同名命令。

## 命令行契约

成熟安装器至少应具备：

- `--help` 与脚本版本。
- `--version latest|X.Y.Z`。
- `--method binary|package`。
- `--mirror`、`--proxy` 和自定义安装目录。
- `--force`、`--uninstall`、`--dry-run`。
- `--yes` 只控制升级确认，不要让 `--force` 绕过版本方向策略。
- `--verbose`，输出候选通道、实际请求 URL 与最终决策，但不泄露认证头。
- 明确的非零失败状态。
- `NO_COLOR` 支持，便于日志系统采集。

参数应在联网或修改系统前完成验证。互相冲突或当前模式不支持的参数应明确报错，不能静默忽略。

verbose 应是安装器自己的结构化日志，而不是简单传递 `curl -v`。后者会产生大量 TLS/请求头噪声，并可能暴露代理认证信息。推荐记录：

- 请求方法及脱敏后的 URL。
- auto 候选顺序、失败候选和最终选中通道。
- latest 版本的解析来源。
- CPU、libc、Release target 与资产名。
- checksum 来源和校验模式。
- 本地/远程版本比较，以及 skip/install 决策。
- 升级方向和确认来源（交互或 `--yes`），以及拒绝降级的原因。
- 最终安装方式与目标路径。

URL 中的 `user:password@` 和查询参数应脱敏。标准代理环境变量可以报告变量名及脱敏地址，但不能输出认证请求头。

## Bash 实现注意事项

- 使用 `#!/usr/bin/env bash`，并明确不能通过 `sh script.sh` 执行。
- 启用 `set -Eeuo pipefail`，同时理解函数位于 `if`/`||` 条件中时 `errexit` 的特殊语义。
- 所有路径变量都使用双引号，数组用于可选参数。
- 不使用 `eval`，不把远程响应作为 shell 代码执行。
- 读取 `/etc/os-release` 时将 `VERSION`、`ID` 等变量局部化，避免覆盖脚本变量。
- 日志写入 stderr；函数需要返回路径等数据时只在 stdout 输出该数据。
- 不依赖 `jq` 完成简单重定向解析，从而降低最小依赖。

## 验证清单

提交前至少运行：

```bash
bash -n install_tool.sh
shellcheck -x install_tool.sh
```

并覆盖以下行为：

- `--help` 和非法参数。
- package 的 dry-run。
- 固定版本 Release 下载、校验、安装、运行和卸载。
- latest 重定向解析。
- 国内镜像通道。
- 目标文件冲突和 PATH 警告。
- 新安装、同版本、升级确认、拒绝降级和非交互确认。
- 临时目录中完成端到端测试，不能污染真实用户安装目录。

跨架构映射不能只靠当前机器测试；还应对照上游 Release 资产清单逐项审阅。
