# Nginx 429 限流与 Google 爬虫

> 配置现状：`site_global` 已由 `7r/s` 放宽为 `15r/s`（`com_limit_zone.conf`），`burst` 仍为 `5`。下文日志统计与本地复现是在 `7r/s` 期间采集的，用于说明触发机制；按当前速率，持续压测时的 429 门槛相应提高。

## 结论先说

- **普通用户：会触发 429**，但只在少数路径上，而且阈值很低。首页、文章页、普通页面不受这套 `limit_req` 影响。
- **Googlebot：不会被这套规则 429**。它跳过了 `user_limit`/`bot_limit`/Apple 相关桶，只剩 `site_global`（当时 `7r/s`，现为 `15r/s`）兜底。抽样日志中 Googlebot 请求 **0 次 429**。
- 真正生效的是 `com_js_signed.conf` 里的 location；`com_limit_rate.conf` 里的同名 product/shop location 因为按顺序先被前者匹配，**实际上已经被覆盖**。

---

## 1. 配置生效链路

所有站点 vhost 都这样引用：

- `/www/server/panel/vhost/nginx/*.conf` → `include com_basic.conf` + `include com_limit_rate.conf`
- `com_basic.conf:29` → `include com_js_signed.conf`

所以限流实际来自：

- `com_limit_zone.conf` 定义桶
- `com_ua_map.conf` 决定 key
- `com_js_signed.conf:387-405` 和 `:592-598` 在 location 里执行 `limit_req`

限流路径是：

```nginx
location ~ ^/(product|shop|category|cart|checkout|account|admin) { ... }
location ~ ^/wp-json/wp/v\d+/products?(/|$) { ... }
```

即：`/product/...`、`/shop/...`（**包括 `/shop/page/2` 这种分页**）、`/category...`、`/cart...`、`/checkout...`、`/account...`、`/admin...`，以及 `/wp-json/wp/v2/product(s)`。

---

## 2. 各限流桶与谁命中

| zone | key | 速率 | burst | 命中者 |
|---|---|---|---|---|
| `user_limit` | `$binary_remote_addr`（仅 `$allow_bot=0`） | **2r/m** | 7 | 普通浏览器 UA |
| `bot_limit` | `$binary_remote_addr`（允许的 bot 且不在 `$se_unlimited`） | 3r/m | 1 | 主要是 AI 爬虫 |
| `apple_global` | `$server_name:applebot` | 100r/m | 20 | Applebot，按站 |
| `apple_total` | 常量 `"applebot"` | 5r/s | 20 | Applebot，全机共用 |
| `site_global` | `$server_name` | **15r/s**（原 7r/s） | 5 | **所有**命中上述 location 的请求，含 Google |

`com_ua_map.conf:60-86` 的关键逻辑：

```nginx
map $http_user_agent $se_unlimited {
    default 0;
    ~*google 1;
    ~*bing 1;
    ~*applebot 1;
}
map "$allow_bot:$se_unlimited" $bot_limit_key {
    default "";
    1:0 $binary_remote_addr;   # 只有 AI 等非搜索 bot 才进 bot_limit
}
map $allow_bot $user_limit_key {
    0 $binary_remote_addr;     # 普通用户
    1 "";                      # 白名单 bot 跳过
}
```

---

## 3. 普通用户为什么会被 429

`user_limit` 是 **`rate=2r/m`、`burst=7 nodelay`**：

- 瞬时最多放行 **8 个**请求（1 + burst 7）
- 之后每 **30 秒**才恢复 1 个
- 第 9 个受限路径请求开始返回 429

而且这个 zone 定义在 `http` 级别，key 只有 `$binary_remote_addr`，所以：

- **同一 IP 在全部站点之间共享同一个 2r/m 桶**
- NAT、公司出口、运营商 CGNAT 后面的多个真实用户会互相挤占
- 首次访问产品页时：无 `sc2` Cookie 的请求先消耗 1 个 token 并 302 到挑战页，验证后重新请求产品页再消耗 1 个 token，**首访实际约消耗 2 个 token**

我在测试环境用本地请求做了验证（用随机 `X-Forwarded-For` 隔离桶，0.2 秒间隔）：

```
普通 UA /product/     : 302×8，然后 429×6
普通 UA /shop/page/2  : 302×8，然后 429×6
普通 UA /blog/        : 302×12，无 429
```

也就是说：**普通用户快速浏览 9 个以上产品页/分类页/购物车/账户页，就会 429**；浏览博客、首页不会。

生产日志佐证：

- `/product` 相关的 429 中，绝大多数是 Applebot
- 排除 Applebot/Google/Bing 后，浏览器类 UA 的产品页 429 仍有少量
- 其中部分 referer 是 `https://www.google.com/`
- 不过样本里有明显的分布式爬虫特征（同一产品 URL、同一秒、多个不同 IP），所以不全是真实用户

另外还有一个放大因素：`site_global` 的 `burst=5`。我在 `7r/s` 时快速连发，普通 UA 第 7 个请求就因 `site_global` 先触发 429；速率提到 `15r/s` 后，瞬时并发仍受 `burst=5` 约束（同一站点短时间超过 1+5 个产品页请求即 429），但持续请求的恢复速度更快。

## 4. Googlebot 为什么不会 429

Googlebot 的 UA 同时命中：

- `$allow_bot ~*Google` → `1`
- `$se_unlimited ~*google` → `1`

于是：

- `$user_limit_key` = `""` → `user_limit` 桶跳过
- `$bot_limit_key` = `""` → `bot_limit` 桶跳过
- `$apple_key` / `$apple_total_key` = `""` → Apple 桶跳过
- 只剩 `site_global`（key 是 `$server_name`，现为 15r/s，burst 5）

抽样时段的日志统计：

- Google 系、Bing 系请求均 **0 次 429**
- Applebot 请求中约 **13%** 为 429

关于 Googlebot 的 403：

- 大部分是**伪造 Googlebot** 的 IP，反向 DNS 验证失败 → 403
- 真正 Google IP 段（66.249.x 等）的 403，我抽查到的基本都是 `?add-to-cart=...`，被 `com_basic.conf` 的购物车规则拦截，属于预期行为
- 不是 429 问题

理论上的例外：`site_global` 是全站共享的。如果某个站点的这些路径总请求量超过约 15r/s（或瞬时 burst 超过 5），**Googlebot 也会被连带 429**。本次统计未出现，但 Applebot 洪水会消耗同一个 `site_global` 桶，存在连带风险。

---

## 5. 注意事项

- **Applebot 被限得很重**：抽样时段 Applebot 请求中约 13% 为 429，来自 `apple_global 100r/m` 和 `apple_total 5r/s` 全机封顶。如果在意 Apple 搜索收录，需要调这两个值。
- **`X-Forwarded-For` 全信任**：`real_cdn_ip.conf` 是 `set_real_ip_from 0.0.0.0/0` + `real_ip_header X-Forwarded-For` + `real_ip_recursive on`。客户端可以随便伪造 XFF 换桶绕过 429(不过为了方便我修改反向代理服务器,简单起见这一块暂不做精细约束)。若走 Cloudflare，建议改用受限网段的 `cf-realip.conf`。
- **路径正则没有边界**：`^/(product|shop|category|cart|checkout|account|admin)` 会顺带匹配 `/production`、`/product-tag`、`/product-category`、`/administrator`、`/admin-panel`、`/shopify` 等，日志里确实出现了这些路径的 429。
- **`com_limit_rate.conf` 的 location 是死配置**：`com_basic.conf` 先 include，`com_js_signed.conf` 的更宽正则先匹配；`com_limit_rate.conf` 的 `^/(product/|shop/...)` 永远轮不到。调参时应直接改 `com_js_signed.conf`。

## 6. 如果想让普通用户完全不 429

可选方案（需要的话我可以直接改并 `nginx -t`）：

- **最直接**：把 `com_limit_zone.conf:12` 的 `rate=2r/m` 提到 `30r/m` 或 `60r/m`，同时把 `com_js_signed.conf` 里的 `burst=7` 提到 `15~20`。
- **更合理**：不要用 `$allow_bot` 作为 `user_limit` 的 key，改为只对可疑 UA（如 `$bad_bot`）或“未通过 JS 挑战”的请求限流，正常浏览器不进入这个桶。
- **站点总桶**：`site_global` 已放宽到 `15r/s`、`burst 5`；若站点并发仍偏高，可继续上调速率，或把 `com_js_signed.conf` 里的 `burst` 提到 `15~20`，也可改成按 IP + 站点。
- **保留 Google 现状**：如果只想限制非搜索 bot，Google/Bing 现在的豁免逻辑是生效的，不需要动。

总结一句：**这套配置不是“只限爬虫”，它对普通用户在 product/shop/cart/account 等路径上施加了 2 次/分钟、突发 8 次的严格限制；Googlebot 则确实被豁免，只剩站点级 15r/s 兜底（原 7r/s）。**
