## 部署流程

反代方案脚本的部署分两步：先拉取仓库，再按方案执行对应脚本。首次部署与后续更新使用同一套脚本。

`base.sh`、`multi.sh`、`tenants.sh` 默认会调用 `update_repos.sh` 更新仓库；不想改动仓库时加 `--no-update-code`(`base.sh` 用 `-D` 调试模式)。

### 1. 拉取仓库

直接执行仓库自带的 `update_repos.sh`：首次运行会克隆到 `~/repos/scripts` 并建立 `~/sh` 链接，之后重复执行即更新。

```bash
bash <(curl -SfL https://raw.githubusercontent.com/xuchaoxin1375/scripts/refs/heads/main/wp/woocommerce/woo_df/sh/update_repos.sh)
```

仓库已在本地时用 `bash ~/sh/update_repos.sh`；只想更新代码可用 `git -C ~/repos/scripts pull`。该脚本默认只更新代码，加 `-U` 同步 shellrc，加 `-g`/`-f` 更新 nginx 等配置文件(`-f` 强制覆盖，酌情使用)。手动克隆的完整步骤见 [sh/README.md](../../../README.md)。

### 2. 选择方案并执行

前置条件：Linux 服务器与 root 权限(写 nginx 配置、重载服务需要)；已安装 nginx 或 openresty，脚本不负责安装 nginx。

后文命令使用反代脚本目录变量；单独开新会话时先重新执行这一行：

```bash
reverse_proxy_scripts=~/sh/nginx_conf/reverse_proxy/scripts
```

宝塔环境的 `-l` 日志目录按实际安装调整，默认通常是 `/www/wwwlogs/`；后文示例里的 `-l /www/logs/` 只作占位，照做时换成实际目录。日志清理默认只扫描 `/var/log/nginx` 与 `/www/wwwlogs`，用了别的目录要在清理脚本里补上。

#### 单机 simple：所有域名转同一后端

```bash
# 标准 nginx 路径
bash "$reverse_proxy_scripts/base.sh" -i <upstream_ip>

# 宝塔路径
bash "$reverse_proxy_scripts/base.sh" -c /www/server/nginx/conf -d /www/server/panel/vhost/nginx -l /www/logs/ -i <upstream_ip>
```

#### 单机 hostmap：按 Host 分流到不同后端

```bash
# 标准 nginx 路径
bash "$reverse_proxy_scripts/base.sh" -G hostmap

# 宝塔路径
bash "$reverse_proxy_scripts/base.sh" -c /www/server/nginx/conf -d /www/server/panel/vhost/nginx -l /www/logs/ -G hostmap
```

生成 `gateway.conf` 与 `gateway/maps/routes.map.conf`；映射表已存在时不会被覆盖，后续按 [不同反代模式下(hostmap)nginx目录结构参考.md](<不同反代模式下(hostmap)nginx目录结构参考.md>) 维护。

#### 多出口 IP：反代服务器与后端一一对应

```bash
# 标准 nginx 路径
bash "$reverse_proxy_scripts/multi.sh" -m 'B1_IP->A1_IP' -m 'B2_IP->A2_IP'

# 宝塔路径
bash "$reverse_proxy_scripts/multi.sh" -c /www/server/nginx/conf -d /www/server/panel/vhost/nginx -l /www/logs/ -m 'B1_IP->A1_IP' -m 'B2_IP->A2_IP'

# 预览：只输出生成的配置，不写文件、不 reload
bash "$reverse_proxy_scripts/multi.sh" --dev -m 'B1_IP->A1_IP'
```

#### 多租户：每租户独立 listen IP 与路由表

```bash
# 标准 nginx 路径
bash "$reverse_proxy_scripts/tenants.sh" -t 'a=P_IP_A' -t 'b=P_IP_B'

# 宝塔路径
bash "$reverse_proxy_scripts/tenants.sh" -c /www/server/nginx/conf -d /www/server/panel/vhost/nginx -l /www/logs/ -t 'a=P_IP_A' -t 'b=P_IP_B'
```

路由用 `-r '<id>:<host>-><backend>'` 追加，或用 `-R` 读取路由文件；预览加 `--dev`。默认保留已有租户的 `routes.map`。

#### 巡检与清理

```bash
# 只检查现状，不删文件
bash "$reverse_proxy_scripts/clean.sh" --status

# 切换模式前：清理全部方案的 D 侧残留，默认保留 map 数据
bash "$reverse_proxy_scripts/clean.sh" --mode all --force
```

清理范围与副作用见 [clean@清理说明.md](clean@清理说明.md)。

#### 端口与防火墙检查

```bash
# 只检查
bash "$reverse_proxy_scripts/check_ports.sh" --ports 80,443

# 未放行时尝试放行
bash "$reverse_proxy_scripts/check_ports.sh" --fix --ports 80,443
```

## 部署后验证

```bash
nginx -t
nginx -s reload

curl -sS http://127.0.0.1/__b_health                             # simple / multi
curl -sS -H 'Host: <domain>' http://127.0.0.1/__gateway_health   # hostmap
curl -sS -H 'Host: <domain>' http://<tenant_listen_ip>/__tenant_health   # tenants
```

健康检查地址由对应模板或脚本生成；多出口与多租户场景把地址换成实际 listen IP。

## 日志清理与定时任务

反代的 `access_log` 默认按请求逐条写入，访问量稍大就会在几天内长到 GB 级。日志写满磁盘后，nginx 会先出现写日志失败，随后影响站点、数据库与 SSH 登录，所以部署完成、流量验证通过后**必须**配置周期清理。

各模式的日志文件名（默认写在 `-l` 指定的目录）：

| 模式 | access 日志 | error 日志 |
| --- | --- | --- |
| simple | `b_to_a_access.log` | `b_to_a_error.log` |
| hostmap | `access.log` | `error.log` |
| multi | `b_<出口IP>_to_a_<后端IP>_access.log` | `b_<出口IP>_to_a_<后端IP>_error.log` |
| tenants | `tenant-<id>-access.log` | `tenant-<id>-error.log` |

`multi` 的日志名会把 IP 里的 `.`、`:` 换成 `_`，例如 `b_1_2_3_4_to_a_5_6_7_8_access.log`。

标准安装的日志目录是 `/var/log/nginx/`，宝塔常见为 `/www/wwwlogs/`；脚本参数 `-l` 传了别的目录时，以实际目录为准。

### 清理脚本

仓库自带 [clean_reverse_server_logs.sh](../../../clean_reverse_server_logs.sh)：用 `truncate -s 0` 清空文件内容，不删除 inode，nginx 不需要 `reload` 就能继续写，也不会出现“日志删了但磁盘空间没释放”。

脚本默认扫描 `/www/wwwlogs` 与 `/var/log/nginx`，只处理文件名含 `access.log` 或 `error.log` 的文件，结束前输出 `df -h`。部署后先手动执行一次：

```bash
bash ~/sh/clean_reverse_server_logs.sh
df -h
```

使用前确认：

- 日志目录不是上面两个默认路径时，把目录补进脚本顶部的 `dirs` 数组，否则定时任务扫不到。
- `all.log`、`warn.log`、`spider.log`、`imgs.log` 这类聚合日志不在匹配范围内；如果同时启用了这些日志，需要扩充脚本的 `-name` 条件。
- 当前匹配 `*access.log*`/`*error.log*` 会连带命中已轮转的 `access.log.1`、`access.log.2.gz`；需要保留归档时，把条件收窄为 `-name "*access.log" -o -name "*error.log"`，或排除 `*.gz`。
- 脚本只清空内容，不做归档；需要按天保留历史时改用本节后面的 `logrotate` 方案。
- 脚本按目录和文件名匹配，不区分站点；同一台机器还跑业务站点时，这些站点的 `access.log`/`error.log` 也会被一起清空。需要保留的日志应换目录，或把 `find` 限定到反代专属前缀。
- Debian/Ubuntu 的 nginx 包通常自带 `/etc/logrotate.d/nginx`，先确认它是否已经在轮转 `/var/log/nginx/*.log`；已有配置就保留它，不要再用本节的 cron 清同一批文件。

### 写入 `/etc/cron.d`

推荐把任务放到 `/etc/cron.d/` 的独立文件，整份覆盖、整份删除，不影响其他计划任务：

```bash
sudo tee /etc/cron.d/clean-reverse-logs >/dev/null <<'EOF'
SHELL=/bin/bash
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
MAILTO=""
# 每天 00:10 清空反代 access/error 日志;truncate 不需要 reload nginx
10 0 * * * root /bin/bash /root/sh/clean_reverse_server_logs.sh >> /root/clean_log_actions.log 2>&1
EOF
sudo chmod 644 /etc/cron.d/clean-reverse-logs
```

要点：

- `/etc/cron.d` 每行比用户 crontab 多一个**用户字段**：`分 时 日 月 周 用户 命令`。直接把 `0 0 * * * bash ...` 拷进去会把 `bash` 当成用户名，任务不会执行。
- 命令、脚本和重定向目标都用绝对路径；`~`、`$HOME` 在 cron 环境下不要依赖。示例里的 `/root` 按实际登录用户替换。
- 文件名不要带点号（`clean-reverse-logs` 而不是 `clean.reverse.logs`）；属主 `root:root`、权限 `644`，文件末尾保留换行，否则 cron 可能忽略。
- 时间避开整点与 `logrotate` 的默认窗口，例如 `10 0 * * *`；不要同时在 root crontab、宝塔面板计划任务里重复配置同一脚本。
- 动作日志 `clean_log_actions.log` 只记录每次执行结果，增长很慢；长期保留可一并纳入 `logrotate`。
- 确认 cron 服务在运行：Debian/Ubuntu 为 `cron`，CentOS/RHEL 为 `crond`。

```bash
# 检查是否重复配置
sudo crontab -l | grep clean_reverse_server_logs
sudo grep -rn clean_reverse_server_logs /etc/crontab /etc/cron.d/ 2>/dev/null

# 检查 cron 服务
sudo systemctl status cron    # Debian/Ubuntu
sudo systemctl status crond   # CentOS/RHEL
```

服务未运行或未设开机启动时执行：`sudo systemctl enable --now cron`(CentOS/RHEL 换成 `crond`)。

### 验证

```bash
# 手动执行,确认能清空并写日志
sudo /bin/bash /root/sh/clean_reverse_server_logs.sh
sudo tail -n 20 /root/clean_log_actions.log

# 看 cron 是否触发(Debian/Ubuntu)
sudo grep CRON /var/log/syslog | tail -n 10
# 或
sudo journalctl -u cron --since today | grep clean_reverse

# 次日确认日志大小与磁盘
sudo ls -lh /var/log/nginx/ /www/wwwlogs/ 2>/dev/null
df -h
```

首次配置可以把时间设到最近几分钟，确认 cron 真的触发后再改回低峰时间。手动执行成功不代表 cron 能跑，`PATH`、权限、换行与文件名都可能让它静默失败。

### 需要保留日志历史

`truncate` 不保留历史，适合“日志只用于排障、过期即丢”的场景。需要按天保留、压缩归档时改用 `logrotate`：

```bash
sudo tee /etc/logrotate.d/nginx-reverse >/dev/null <<'EOF'
/var/log/nginx/*.log /www/wwwlogs/*.log {
    daily
    rotate 7
    compress
    delaycompress
    missingok
    notifempty
    copytruncate
}
EOF
```

`copytruncate` 同样不要求 nginx `reload`，但和上面的 cron 清理**二选一**，同时启用会把刚轮转的归档再次清空。

## 更新与切换

- 更新仓库：`git -C ~/repos/scripts pull`；需要同步 shellrc 时用 `bash ~/sh/update_repos.sh -U`，需要更新 nginx 等配置文件时加 `-g`(`-f` 强制覆盖)。
- 切换方案：先 `bash "$reverse_proxy_scripts/clean.sh" --status` 巡检，再用 `bash "$reverse_proxy_scripts/clean.sh" --mode all --force` 清掉 D 侧残留，最后执行新方案脚本。
- 固定当前检出：给 `base.sh` 加 `-D`，给 `multi.sh`、`tenants.sh` 加 `--no-update-code`。

## 在线执行(可选)

不准备克隆仓库时，把脚本地址换成 raw 前缀，参数与本地执行一致：

```bash
RAW='https://raw.githubusercontent.com/xuchaoxin1375/scripts/refs/heads/main/wp/woocommerce/woo_df/sh/nginx_conf/reverse_proxy/scripts'
bash <(curl -SfL "$RAW/base.sh") -i <upstream_ip>
```

把 `base.sh` 换成 `multi.sh`、`tenants.sh`、`clean.sh`、`check_ports.sh` 即可；国内可把 `RAW` 换成 gitee 前缀 `https://raw.giteeusercontent.com/xuchaoxin1375/scripts/raw/main/wp/woocommerce/woo_df/sh/nginx_conf/reverse_proxy/scripts`。`base.sh`、`multi.sh`、`tenants.sh` 在线执行时仍会自动更新仓库。
