# 决策记录（WebUI 单一前端重建）

- 日期：2026-10-07；决定：FastAPI + 单文件原生前端（当时为 `webui/v1/dist/index.html`，v1 已于 2026-11-16 移除），后端 `/api/v1` 为主 + `/api` 兼容。
- 为什么：仅自己本机用，浏览器打开最快；无 Node 重依赖，`npm run build` 仅复制；复用引擎 `SPEED_PRESETS`/校验/失败清单，不由前端算。
- 放弃了：Vite+React（交互更强但需工具链）、Tauri 桌面壳（要窗口托盘才需要）、双前端（历史主败因）。
- 假设：Python 3.9+ 且愿装 fastapi/uvicorn；契约沿用 WEBUI_LESSONS 第一节；无需对外监听。

## 最新 skill 落地（2026-10-08，复用口径：直觉层冻结，功能层自定义）

- 复用项：工具栏九层骨架（搜索＋筛选草稿应用＋显示＋导入＋导出＋新增 primary 最右）、计数条、复选列、排序与 `aria-sort`（原三态，2026-11-16 改为两态，见文末）、代理与 TTL 与备注与详情与警告列、短名显示、列宽调节（热区＋键盘步长＋还原＋持久）与显示区重置、行内展开与新增卡共用同一表单同一校验、悬浮批量条与删除撤销、导入预检门、窄屏卡片。功能接线（列定义、字段、导航项、校验函数体）按本机运维业务重写，对接真实接口。
- 有意未做（非目标，配套元素不留半套）：
  - 配额上限数：无配额查询接口，计数条如实显示条数，不虚构上限。
  - 记录编辑草稿持久化：编辑仅实例内，符合表单规范；操作页新建类表单已持久化草稿。

## 2026-11-15 草稿与正式施工的边界

- 决定：设计草稿只用于确认布局、信息架构与交互方向，不作实现目标；正式实现按 `admin-console-design` 的完整状态模型与验收底线补齐。
- 为什么：`drafts/draft-b.html` 只有顶栏折叠按钮和静态页脚，v2 按草稿落地时漏掉 fable 外壳的 Rail 悬停/键盘临时展开、页脚收起/展开、Esc、`[` 快捷键与覆盖式槽宽不变；这些项在 v1 的 `TASKS.md` 已有记录，重写时没有回查。
- 后果：施工前列 skill 对照清单，草稿未覆盖的条目默认纳入；验收补测悬停/焦点 peek、Esc、页脚按钮、主内容几何不变与快捷键，只测草稿画出的按钮不算完成。

## 2026-11-16 记录表列宽与排序缓存

- 决定：记录表按总量分档。首次请求 50 条：`total <= 50` 直接本地；`51–500` 再用 `all=true` 取一次全量；`>500` 保持服务端分页。补齐 sonnet 式列宽调节；排序改为三态（2026-11-16 晚改两态，见下一条）。编辑/批量改内容成功后直接更新前端缓存；批量删除本地移除并在服务端分页模式下后台刷新当前页。
- 为什么：用户实际 zone 通常不超过 10 条，分页下每次排序都请求后端不符合参考稿的即时体验；但直接对所有 zone 全量加载又会让大 zone 首包和内存变大。按总量分档兼顾两种规模。
- 范围：后端保留服务端分页与排序接口供大 zone/导出使用，并加 30 秒记录缓存减少切换域名/刷新的重复 Cloudflare 请求；`POST /api/v1/records/refresh` 供“刷新”按钮显式绕过。导入因响应不带完整记录，成功后后台重拉一次。
- 后果：阈值固定为 500，超过后排序/筛选/翻页仍会请求后端（缓存命中后通常很快）；外部在 Cloudflare 控制台改记录后，需等缓存过期或点刷新才可见。

## 2026-11-16 跨账号查找改为后台扫描

- 决定：v2 的跨账号查找使用 `POST /api/v1/find/scans` 创建内存扫描，`GET /api/v1/find/scans/{id}` 轮询进度，`POST /api/v1/find/scans/{id}/cancel` 取消；v2 默认 `stop_on_first=true`（命中一个账号即停止），可切换“扫描全部账号”；旧 `GET /api/v1/find?domain=` 保留同步兼容，并保持扫描全部账号。
- 为什么：59 个账号串行扫描实测 78.6 秒，页面只有按钮转圈，用户会把等待误判为无结果；原实现只查 `status=active`，pending/moved 会被误报为不存在；命中后同步拉取全部 DNS 记录又放大延迟。多数查找只需要确认“在哪个账号”，命中即停更符合实际使用。
- 范围：扫描只按 zone 名查询一次，不拉 DNS 记录，不按 active 过滤；每账号记录 hit/miss/error；命中即停或取消时，剩余账号标记为“未检查”，不混入“未找到”或“失败”；界面显示已检查数、未检查数、当前账号、命中/未找到/失败与结构化扫描记录；扫描不写入任务历史。
- 继续查询：命中即停或取消后，页面提供“继续查询剩余 N 个账号”，在原扫描上继续检查未检查账号；继续阶段使用原扫描速度且不再提前停止，结果、未找到与失败计数累加，全部检查完后 `complete=true`。
- 后果：扫描结果在内存中保留最近 20 个，服务重启后丢失；命中即停只保证“至少一个命中”，不保证全局唯一或全部账号；需要完整结果时可继续查询或取消勾选再扫；旧同步接口仅作兼容；任务日志结构化另做。

## 2026-11-16 任务日志改为结构化时间线

- 决定：Job 追加日志时同时记录时间戳；`/api/v1/jobs/{id}/logs` 返回原始 `logs` 与结构化 `events`；前端主视图显示执行时间线，原始 CLI 文本折叠在“原始日志（排障用）”。
- 为什么：原实现把引擎 CLI 的 `====` 分隔线、`key=value`、`[DRY-...]` 原样塞进 `<pre>`，不像 Web 界面；错误与账号汇总也难以扫读。
- 范围：解析已知前缀（INFO/WARN/ERR/DRY/FOUND/MISS/CHECK/ACCOUNT-*/VERDICT 等），参数行并入“任务开始”，缩进行并入上一条详情；未识别噪声只保留在原始日志，不进入时间线。
- 后果：解析器是展示层适配，不改变引擎输出；新增日志前缀需要补映射；原始日志仍保留用于排障与下载。

## 2026-11-16 邮箱转发先验证再启用

- 决定：Cloudflare Email Routing 按“先添加并验证目标地址、再启用路由并设置 catch-all”实现；目标地址按账号共享，验证一次可复用到同账号其他域名。
- 为什么：目标地址验证是异步邮件步骤；未验证就切 MX，catch-all 不会生效，来信会被 Cloudflare 拒绝（Address does not exist），已有邮箱可能中断。
- 范围：WebUI 只配置 catch-all；按前缀的 routing rule、重发验证邮件、删除目标地址仍在 Cloudflare 控制台。provision 表单在目标邮箱未验证时给出中断风险提示，本轮不调整引擎既有执行顺序。
- 后果：新增 `/api/v1/email-routing/addresses`、`status`、`complete` 契约与目标地址状态面板；真实账号首次使用需 API Token 具备 Email Routing Addresses / Rules / Settings 权限，并先在目标邮箱完成验证。

## 2026-11-16 邮箱转发面板按账号级/域名级双列分层

- 决定：`EmailRoutingPanel` 采用 A2 双列工作台。左列账号级目标地址库负责账号选择、地址列表、验证状态与添加；右列域名级启用只负责域名、目标、状态和完成配置。已验证地址默认选中，待验证地址折叠在“账号内待验证地址”里；风险确认与高级详情按需展开。
- 为什么：目标地址是账号级资源，验证一次可复用于同账号任意域名；把它和域名级启用混在同一表单，会让用户误以为每个域名都要重新输入和验证。双列把“先选/验证地址，再启用域名”的依赖关系直接画出来，也避免状态区一次暴露全部技术字段。
- 范围：只改邮箱转发面板；`ProvisionPanel` 与 `Inspector` 的目标邮箱字段保持原样，后续再评估是否统一到账号级已验证地址选择器。1024px 及以下双列堆叠；待验证地址被选中时自动展开；API 契约不变。
- 后果：完成配置前必须先有已验证目标地址；切换账号会清空域名与目标选择；已有 catch-all 或非 Cloudflare MX 时仍走内联二次确认。A1 单列草稿保留在 `drafts/email-routing/draft-a.html` 供回退。
- 后续：Provision 与 Inspector 的目标选择已在下条“邮箱转发未验证不再预切换 MX”中统一。

## 2026-11-16 邮箱转发未验证不再预切换 MX

- 决定：`configure_email_routing` 在目标邮箱未验证时只确保目标地址存在并返回 `pending_verification`，不读取所需记录、不写 DNS、不启用路由；`ProvisionPanel` 与 Inspector 的邮箱目标只列账号内已验证地址，缺少已验证目标时阻断预览/执行。
- 为什么：旧顺序会先补 MX/启用路由，再因未验证而不设 catch-all；期间来信可能被拒。目标验证是外部异步步骤，未确认前不能切换生产收信。
- 范围：CLI `--provision`、WebUI 任务与 API 共用同一引擎方法，因此一并生效；已有已验证目标的行为不变。`ProvisionPanel` 关闭邮箱步骤后仍可执行其他步骤；Inspector 留空目标即跳过邮箱步骤。
- 后果：未验证目标不再产生任何 zone 级邮箱改动；此前依赖“先切 MX 再等验证”的流程需要改为先验证再执行。取代“2026-11-16 邮箱转发先验证再启用”中“本轮不调整引擎执行顺序”的结论。

## 2026-11-16 出口代理保存列表与开关分离

- 决定：新增 `GET/PUT /api/v1/proxy`，顶栏代理徽标与侧栏页脚打开设置弹窗；当前进程保存代理列表，总开关控制是否启用，每条代理另有单项开关。点“保存配置”按总开关与单项开关重建内存代理池。
- 为什么：本机直连 Cloudflare 有时偏慢；只靠启动参数要停服重启。用户还需要保留多个代理、只启用其中几个，并能在不删除配置的情况下整体停用，因此不能把“保存”等同于“启用”。
- 范围：代理 URL 仅支持 HTTP/HTTPS；`GET` 返回脱敏地址与稳定 id，已有条目只传 id 即可切换开关，服务端保留原凭据；新增条目必须带 url。总开关关闭时仍保存列表但不建代理池；空列表表示清空。审计只记总数、启用数与模式，不记 URL 与凭据。进行中的任务仍持有原代理池，保存后新发起的请求才生效。
- 后果：配置只驻内存，重启 WebUI 后回到启动参数或直连；`serve-webui.ps1 -Restart` 也不会保存页面内设置。启动参数会作为初始列表（全部启用、总开关开），页面可继续增删或关闭。需要固定代理时仍用 `-Proxy` / `-ProxyFile`。

## 2026-11-16 记录表排序列头改两态

- 决定：v2 记录表表头排序改为两态——点新列从升序开始，再点同列在升序/降序间切换，不再点回“未排序”；回到 Cloudflare 返回顺序用工具栏“重置排序”（排序激活时出现），窄屏用工具栏“排序”下拉里的“默认顺序”。
- 为什么：三态（升 → 降 → 无）从降序切回升序要点两下，第三次点击静默取消排序用户也料不到；单人运维场景“点一下换方向”比“保留还原能力”更常用。参考 skill 允许按产品采用两态，故不算违约。
- 范围：只改 v2；≤1023px 卡片视图此前没有任何排序入口，本次在工具栏补“排序”下拉（桌面隐藏，避免与表头重复）；`aria-sort` 语义不变，未排序仍为 `none`。
- 后果：验收脚本断言从“第三次点击回到未排序”改为“第三次切回升序 + 重置排序回 none”，并新增 768 卡片视图排序断言；`clearFilters` 仍只清搜索/类型/代理，清排序走“重置排序”或下拉默认项。

## 2026-11-16 新增记录弹窗直接写入

- 决定：v2 的“新增记录”弹窗直接 `POST /api/v1/records`，成功后关闭弹窗并刷新当前记录范围；不再先生成 `dry_run` 预览任务再跳到抽屉执行。预览路径保留在右侧批量抽屉的“添加域名或记录”，与命令行 dry-run 同源。
- 为什么：Cloudflare 官方控制台就是表单直写；单条新增还要经过“预览 → 切抽屉 → 执行”，多两步，也容易找不到刚填的参数。逐条预览的实际价值在批量与命令行场景。
- 范围：弹窗补齐备注与 MX 优先级字段，校验与编辑弹窗一致；后端契约不变（`POST /api/v1/records` 已存在，导入也复用它）；打开新增弹窗不再顺带打开批量抽屉。
- 后果：单条新增成功后按当前范围后台重拉一次（接口不返回新记录 id，无法就地插入缓存）；需要先看再写或一次加多条时仍走批量抽屉。

## 2026-11-16 移除 v1 旧前端

- 决定：删除 `webui/v1/`（源码、构建产物、验收脚本与设计稿）；`start_web_ui.py` 只托管 `webui/v2/dist`；`serve-webui.ps1` 移除 `-V1`/`-V2`，只保留 v2 入口。
- 为什么：v2 已覆盖全部功能并稳定使用，v1 仅作回退；保留两套前端会让交互对齐、构建与验收继续产生双份成本。
- 范围：同步更新 `ReadMe.md`、`webui/README.md`、`USAGE.md`、`REDESIGN.md`、`v2/README.md`、`tools/verify.ps1` 与 `.gitignore`；`/api/v1` 是后端接口版本，不受本次删除影响。
- 后果：`--v1`、`--frontend-v1`、`-V1`、`-V2` 不再可用；如需旧四页界面，只能从 Git 历史取回对应提交。
