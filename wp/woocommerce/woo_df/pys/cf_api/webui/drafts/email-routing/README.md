# 邮箱转发面板 · 方案 A 原型草稿

静态、可点击的原型，用于确认“账号级目标邮箱 + 域名级启用转发”的布局、信息层级和交互方向。
全部是 mock 数据，不调用 `/api/v1`，不写 Cloudflare，也不影响正式 `webui/v2` 页面。

**已选定 A2 双列工作台**，并已在 `webui/v2/src/components/EmailRoutingPanel.tsx` 落地；A1 保留供回退。

## 怎么打开

- 直接双击 `index.html`，或在本目录执行 `python -m http.server 8611` 后访问
  `http://127.0.0.1:8611/index.html`。
- 从仓库草稿入口进入：[../index.html](../index.html)。
- 右上角可切换浅色 / 深色；窄屏拖到 390px 或 320px 检查回流。

## 两版布局

| 草稿 | 布局 | 适用 |
|---|---|---|
| [A1 单列分层](draft-a.html) | 账号级在上、域名级在下 | 首次配置、低频操作、手机/平板；备选 |
| [A2 双列工作台](draft-b.html) | 左侧目标地址库、右侧域名配置 | 多账号多域名、熟练用户；已选定，窄屏自动堆叠 |

两版共用同一套状态与交互，只改布局。已选定 A2：账号级与域名级并排可见，多域名重复配置时切换更少；1024px 及以下自动堆叠。

## 建议重点看的六种状态

顶部“预览状态”可切换：

- **已验证**：默认选中已验证目标地址；域名级主按钮直接可用，不需要再次输入或验证。
- **待验证**：显示待验证卡片和“刷新验证”；域名级明确阻断，不显示可点击的假完成按钮。
- **未添加**：空状态只做一件事——添加并发送验证；域名级保持不可用。
- **已配置**：显示“已启用，catch-all → 目标”，不诱导重复写入。
- **风险冲突**：覆盖其他 catch-all + 非 Cloudflare MX；主按钮进入二次确认，不直接写入。
- **域名未激活**：先解释 zone 状态，再给等待/刷新路径。

另有 **MX 冲突** 和 **自定义** 状态，用于演示“只替换 MX、没有 catch-all 冲突”的确认路径，以及手动改账号/域名后的状态。

## 建议试的操作

- 切换账号 `cf00 / cf01 / cf02 / cf03`，观察账号级地址库和域名状态如何变化。
- 在“已验证”状态点“+ 添加新目标邮箱”，提交一个邮箱；再点待验证条目的“刷新验证”。
- 在“风险冲突”状态点主按钮，查看二次确认；取消后回到原状态。
- 展开“高级详情”，确认 MX、SPF、DKIM 和 routing 原始字段默认不占首屏。
- 在 1440 / 1024 / 768 / 390 / 320 宽度下检查：操作区不挤压、按钮文字不截断、页面无横滚。

## 草稿边界

- 草稿只确认布局、信息层级和交互方向，**不是实现规格**；正式施工按 `frontend-design` /
  `admin-console-design` 补齐加载、空、错、成功、键盘焦点、确认弹窗、API 契约和验收。
- 草稿使用真实 `webui/v2/src/styles.css` 令牌，但不代表正式页面已经改版；正式面板已按 A2 落地，见 `webui/v2/src/components/EmailRoutingPanel.tsx`。
- 草稿里的“添加 / 刷新验证 / 完成配置”都是本地 mock，不会发请求，也不会改变 Cloudflare。
- 没有实现真实的异步等待、轮询、权限不足、API 错误和超时；这些要在正式施工时补。
- 没有做按角色隐藏；当前 WebUI 只有单一访问口令，没有用户/角色模型。

## 正式施工后仍未覆盖

- 风险操作正式版保留内联二次确认，未改成弹窗。
- 待验证状态正式版保留“刷新验证”入口，未加轮询。
- Provision 与 Inspector 已统一从账号级已验证地址中选择目标，未验证目标不再可提交。
