A1 · 备选

单列分层

账号级目标邮箱在上，域名级配置在下；信息层级最清楚，窄屏最自然。

  • 优点：首次配置不迷路；账号级复用关系一眼可见。
  • 代价：桌面宽屏下垂直空间用得比较多。
  • 适合：首次配置、低频操作、手机/平板。

A2 · 已选定

双列工作台

左侧目标地址库，右侧域名配置；桌面一次看全，窄屏自动堆叠。

  • 优点：给多个域名重复配置时切换更少，账号级/域名级关系并排可见。
  • 代价：左列信息密度更高，首次使用要多看一眼。
  • 适合：多账号、多域名、熟练用户。

建议重点看的六种状态

状态 看什么 预期
已验证 账号级目标地址、域名级主按钮 默认选中已验证地址，不需要再次输入或验证；主按钮直接可用。
待验证 待验证卡片、刷新入口、域名级阻断原因 明确“验证完成前不能完成 catch-all”；不显示可点击的假完成按钮。
未添加 空状态表单、主操作数量 首屏只做一件事：添加并发送验证；域名级保持不可用。
已配置 状态摘要、重复操作的处理 显示“已启用，catch-all → 目标”，不诱导重复写入。
风险冲突 覆盖其他 catch-all、非 Cloudflare MX 风险只在决策点出现；主按钮进入二次确认，不直接写入。
域名未激活 zone 状态、阻断提示 先解释为什么不能配置，再给等待/刷新路径。
草稿边界： 草稿只确认布局、信息层级和交互方向，不是实现规格。正式施工会按 frontend-design / admin-console-design 补齐加载/空/错/成功态、 键盘与焦点、确认弹窗、API 契约核对、响应式验收和回归测试；草稿没画到的状态不会省略。
建议试的操作： 切换顶部的“预览状态”；在“已验证”状态点“+ 添加新目标邮箱”并提交； 在“待验证”状态点“刷新验证”，观察它如何变成可复用地址； 在“风险冲突”状态点主按钮，查看二次确认；展开“高级详情”看技术信息是否足够隐蔽。
